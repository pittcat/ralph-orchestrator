# Private v0.1.0 Release — Design Spec

**Date**: 2026-06-05
**Branch**: `pittcat-dev`
**Remote**: `origin → https://github.com/pittcat/ralph-orchestrator` (private)
**Upstream**: `https://github.com/mikeyobrien/ralph-orchestrator`
**Current version**: `2.9.2`
**Target version**: `0.1.0`

## 1. 目标

在 `pittcat/ralph-orchestrator` private fork 上以 `v0.1.0` 发一次"自己可见"的 release：

- 私有 GitHub Release（仅仓库 collaborator = 用户本人可见）
- 4 平台二进制：`aarch64-apple-darwin`、`aarch64-unknown-linux-gnu`、`x86_64-apple-darwin`、`x86_64-unknown-linux-gnu`
- shell 安装脚本 + 校验和
- **不**发布到 npm（公共）
- **不**发布到 crates.io（公共）
- **不**改品牌、**不**重命名 crate、**不**改 repository 字段

## 2. 变更清单

| 文件 | 改动 | 原因 |
|---|---|---|
| `Cargo.toml`（workspace 根） | `version = "2.9.2"` → `version = "0.1.0"` | 全工作空间统一版本号 |

| 9 个子 crate 的 `Cargo.toml` | 无手改（全部用 `version.workspace = true`） | — |
| `Cargo.lock` | 由 `cargo build` 自动重生成并 commit | — |

## 3. 执行步骤

1. **预检**：
   - `cargo check --workspace --all-targets` — 0 错误
   - `cargo build --release -p ralph-cli` — 验证 release profile 能编出来
2. **改配置**：
   - 根 `Cargo.toml` 改两处（version + publish-jobs）
   - `.github/workflows/release.yml` 三个 publish job 加 gate
3. **生成 lock**：`cargo build` 触发 `Cargo.lock` 同步
4. **验证 ralph CLI 二进制**：`./target/release/ralph --version` 期望输出 `ralph 0.1.0`
5. **commit**：`git commit -am "release: v0.1.0"`
6. **打 tag**：`git tag v0.1.0`（**仅本地**，先不 push）
7. **本地确认**：
   - `git log -1 --format=%H` 记录 commit hash
   - `git show v0.1.0 --stat` 确认 tag 内容
   - **暂停**——向用户报告变更总结，请用户确认 push tag
8. **push tag**（用户授权后）：`git push origin v0.1.0`（**只推 tag，不推分支**）
9. **观察 CI**：
   - 监控 `.github/workflows/release.yml` 的 `plan` → `build-local-artifacts` → `build-global-artifacts` → `host` 四个 job
   - `host` job 完成后会创建私有 GitHub Release
   - `publish-crates` / `publish-npm` / `smoke-test-install` / `announce` 全部因 secret 缺失被 skip
   - 整体状态：绿色 ✅
10. **交付确认**：列出 release URL + 4 个二进制资产 + 校验和

## 4. CI Workflow 现状（背景信息）

`.github/workflows/release.yml` 实际包含 8 个 job（`plan` / `build-local-artifacts` / `build-global-artifacts` / `host` / `publish-crates` / `publish-npm` / `smoke-test-install` / `announce`）。

上游 mikeyobrien 维护的 workflow 是按"公开发布到 npm + crates.io"设计的。本次发版目标与该假设冲突，所以 §2 里的 gate 改动是必要的：让 fork 上的 workflow 行为与用户意图对齐（"自己可见 = 不发公共"），而不是依赖 secret 缺失导致 job 失败来间接达到目的。

**具体的 gate 改动（最终方案）**：使用 GitHub repository **variable**（不是 secret）作为开关。变量在 fork 上**默认不存在**，所以 `vars.PUBLIC_RELEASE == 'true'` 始终为 false，publish job 全部 skip，Actions 保持绿色。将来若要启用公共发布，只需在 `pittcat/ralph-orchestrator` → Settings → Variables → Actions 添加 `PUBLIC_RELEASE = true`。

四个 job 的 if 条件统一改为追加 `&& vars.PUBLIC_RELEASE == 'true'`：
- `publish-crates.if`: `... && vars.PUBLIC_RELEASE == 'true'`
- `publish-npm.if`: `... && vars.PUBLIC_RELEASE == 'true'`
- `smoke-test-install.if`: `... && vars.PUBLIC_RELEASE == 'true'`
- `announce.if`: 现有 `always() && ... (needs.publish-crates.result == 'skipped' || needs.publish-crates.result == 'success') && (needs.publish-npm.result == 'skipped' || needs.publish-npm.result == 'success') && (needs.smoke-test-install.result == 'skipped' || needs.smoke-test-install.result == 'success')` 替换为 `... && vars.PUBLIC_RELEASE == 'true' && (skipped-or-success 条件)`，并加 `|| vars.PUBLIC_RELEASE != 'true'` 分支让它在变量不存在时直接成功退出

> 选定 `vars.PUBLIC_RELEASE` 而非 secret 的原因：secret 一旦存在就分不出"我有 secret 但不想发"和"我没 secret"；variable 不存在 = 显式"不发"，存在 = "发"，语义最清晰。

## 5. 不会做的事

- ❌ 不重命名 crate / binary / 文档
- ❌ 不写 `CHANGELOG.md`（未来加）
- ❌ 不改 crate description 字段（保留 "Ralph Orchestrator - Multi-agent orchestration framework"）

## 6. 风险与缓解

| 风险 | 缓解 |
|---|---|
| Cargo.lock 与新版本不匹配 | 预检步骤会触发 lock 重生成 |
| 9 个子 crate 的 `version.workspace = true` 没全部覆盖 | 预检跑 `cargo check --workspace` 会在版本不一致时失败 |
| `publish-jobs = []` 让 cargo-dist 报配置警告 | cargo-dist 0.30.3 支持空数组；如有问题可降级为 `publish-jobs = ["homebrew"]`（homebrew 不存在会自动 skip） |
| `.github/workflows/release.yml` 的 gate 改动语法有误 | 实施时手工核对 if 条件语法；若最终仍有红色 Actions，归因到具体哪个 job 后做 hotfix commit |
| push tag 错了 | 回滚：`git push origin :refs/tags/v0.1.0` + `git tag -d v0.1.0`；配置改动用 `git revert` |
| 私有仓库的 GitHub Actions 分钟数 | 私有仓库 free tier 每月 2000 分钟；4 平台构建预计 10-20 分钟，余量充足 |
